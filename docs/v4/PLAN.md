# 坦克大战 v4.0 · 规划总览：测试与质量

v3.0 把游戏做成了 8 个关卡、自己做地图、双人合作、六个平台的安装包，功能已经够多了。但到现在为止，验证方式只有三种：开发者手动玩、在工程副本里追加脚本截图（[架构文档第 10 节](../ARCHITECTURE.md#10-测试与演示视频)）、CI 里启动桌面版截一张图。**没有一条能自动判断“对不对”的测试**，每次改动都靠人眼看。

v4.0 不加新玩法，专门解决这个问题：**让每条游戏规则都有自动化测试，每个 PR 都能自动跑，并且能量化地说出“测到了多少”**。

| 方向 | 内容 | 状态 | 详细文档 |
|---|---|---|---|
| **1. 测试框架** | 无界面（headless）运行游戏，在引擎里直接调用游戏函数并检查结果，自动判定通过 / 失败 | ✅ 已实现（#26） | [TEST_PLAN.md 第二节](TEST_PLAN.md#二引擎内测试框架) |
| **2. 覆盖测试** | 规则、地图、子弹、敌人、流程状态机、复活与广告、地图编辑器、双人合作、构建工具、网页外壳全部写测试 | ✅ 96 个用例 ID 全部有测试（#27~#46） | [TEST_PLAN.md 第三节](TEST_PLAN.md#三测试用例清单) |
| **3. 覆盖率** | 给工程副本插桩，统计每个函数、每个消息处理是否被执行到；状态机的每条边、每条消息、每条玩法规则都有对应用例 | ✅ 函数 96%、事件处理 98%（子弹相撞抵消的处理受已知问题影响、时有时无，不计入）、消息 100%，有基线（#42、#47） | [TEST_PLAN.md 第四节](TEST_PLAN.md#四覆盖率怎么算) |
| **4. 合入前检查** | 原计划用 GitHub Actions；组织的 Actions 额度用完后改为本地 `pr_check.sh`，报告贴在 PR 里；安装包启动测试本地运行 | ✅ 已实现（#34、#46） | [TEST_PLAN.md 第五节](TEST_PLAN.md#五在本地检查不用-github-actions) |

## 一、为什么现在做测试

- **代码已经不小**：8 个 `.spx` 文件共约 2700 行，108 个函数、58 个事件处理、25 种广播消息；`main.spx` 一个文件就有 1444 行、68 个函数。
- **有容易回归的地方**：[解释器限制](../ARCHITECTURE.md#9-spx-解释器的限制与对策重要)（方法表上限、克隆收不到通用消息、再次广播会打断正在运行的处理）都是“改一行就可能启动不了或者偶发出错”的问题，人工很难每次都想到。
- **有两套必须一致的规则**：地图检查同时存在于 `tools/levels/check.py` 和游戏里的 `edCheck()`，现在没有任何东西保证它们一致。
- **生成文件可能过期**：造型、`UI.spx` 的 `GENERATED` 区块由 `build.py` 生成，忘了重新生成不会有任何提示。

## 二、可行性：原型已经跑通

在 2026-10-24 用本机的 spx 4.0.0 做了验证：复制一份工程，在 `main.spx` 末尾追加一段测试脚本，用 `spx run -headless .` 运行。

```
TEST PASS state starts at home
TEST PASS cellIndex roundtrip
TEST PASS level 1 has 13 rows
TEST PASS startGame -> stPlay
TEST PASS first defeat -> revive prompt
TEST DONE fails 0
```

- 不开窗口，**8 秒**跑完（包括引擎启动），之后脚本调用 `exit` 退出。
- 测试脚本能直接读写舞台变量（`state`、`stage`），调用舞台函数（`levelMap`、`startGame`、`baseDestroyed`），能用闭包写断言函数。
- **进程的退出码永远是 0**，所以必须靠解析输出判断结果：有 `TEST FAIL`、没有 `TEST DONE`、或者超时，都算失败。

这说明“在引擎里测游戏逻辑”不需要改游戏代码，也不需要额外的测试库。详细设计见 [TEST_PLAN.md](TEST_PLAN.md)。

## 三、范围

**做**：

- 自动化测试：构建工具（Python）、游戏逻辑（引擎内）、网页外壳（JavaScript）。
- 覆盖率统计和报告。
- 每个 PR 合入前在本地跑检查（`tools/test/pr_check.sh`），报告贴在 PR 里；发布前本机打包跑启动测试。**不依赖 GitHub Actions**（组织的 Actions 额度有限，2026-10-25 起任务启动不了）。
- 测试中发现的 bug：每个 bug 一个修复 PR，附上能复现它的测试。

**不做**：

- 新玩法、新关卡、新平台。
- 像素级截图比对（现代画风有粒子和震屏，画面每次都不一样，误报会很多）。截图仍然用于 PR 里的人工验证。
- 真实的键盘 / 触屏事件注入：spx 没有提供注入按键的接口，按键处理（`onKey`）只做手工验证，测试直接调用按键背后的函数（例如 `confirm()`、`again()`）。见 [TEST_PLAN.md 第六节](TEST_PLAN.md#六已知限制)。

### 和 v3.0 修复并行时的约定

v4.0 开始时 v3.0 还在修复（例如 [PR #18](https://github.com/Qiniu-ERE/zero/pull/18) 修复 XBuilder 上 `rand()` 的类型问题）。两条线同时进行，按下面的约定避免互相影响：

- **游戏代码的修复走 `main`**：v3.x 的修复照常合入 `main`；v4.0 的测试发现的游戏 bug，修复 PR 也合入 `main`，测试代码合入 `v4.0`。
- **`v4.0` 定期同步 `main`**：每次 `main` 合入修复后，开一个“同步 main 到 v4.0”的 PR，保证测试测的是最新的游戏代码。
- **v4.0 的 PR 不改游戏代码和 `TankBattle.xbp`**（只加 `tests/`、`tools/test/`、文档和 CI），所以和 v3 的修复不会冲突。`.xbp` 是二进制文件，冲突了没法合并。
- **不在 `v4.0` 上推送 `v*` 标签**：推送标签会触发发布流程。`v4.0.0` 只在 `v4.0` 合入 `main` 之后打。
